# Simple Ripple transport timing

This supersedes the manual timing described in `simple-ripple-prototype.md`. Place a Ripple, connect it to Heartbeat (automatic on creation), and press Play. Its surface and separate handle reveal Instrument, Volume, and Period controls. No manual launch is required.

1. **Automatic cycles.** `simple-ripple-loop.js` is serviced by the existing shared audio scheduler. Each emitter has one current cycle, one receiver snapshot, and one Set of committed event indices. SVG rendering only reads transport phase; it schedules no notes. The ring uses a stable emitter ID, so completed and new rings cannot coexist. There is no private clock or timer.

2. **Toy loops and duration.** One toy loop is 384 ticks (four quarters at 96 PPQ). Period offers 1–4 loops, making a cycle 384–1,536 ticks. Radius is `720 × (currentTick − cycleStart) / durationTicks`. The repeat period and expansion duration are the same quantity. Pause freezes it, resume continues it, and Return to Start discards runtime cycles and displays radius zero. Tempo changes update the transport's tick/audio mapping without changing musical duration.

3. **Main Rippler reuse.** The implementation imports `RIPPLER_LOOP_TICKS` and `ripplerCycleAtTick` from `ripplesynth-transport.js`, using the existing shared phase origin of zero. Main Rippler remains unchanged. Its recording quantiser wraps the last cell to offset zero, which would put a spatial arrival at launch; Simple Ripple instead reuses Cannon's established `quantizeBouncerOffsetTick` endpoint policy. The existing application audio scheduler, transport registry, connection graph, instrument picker, volume controls, and shared trash are reused.

4. **Quantisation.** Arrivals use the canonical Cannon helper with division 2: 96 ticks per quarter and 48 ticks per DrawGrid step. This helper rounds arrivals forward and retains the existing strict-next-cell behavior for exact grid contacts. Its final cell is capped at `durationTicks − 1`, preserving the project's established spatial end-cell exception rather than wrapping into the next cycle.

5. **Geometry to musical time.** At each cycle's beginning, eligible `triggerReceiver` objects, receiver pitch, emitter origin, and nearest-bound distance are snapshotted. Intended tick is `cycleStart + distance / 720 × durationTicks`; the shared quantiser then resolves the event tick. Rectangle rotation, circular bounds, and source overlap use the existing generic wave-distance helper. Out-of-range objects are skipped. Moving a receiver or emitter leaves the travelling wave unchanged; the next cycle uses the new geometry. Receiver IDs are deduplicated per snapshot. Cube geometry is never moved to fit a grid.

6. **Receiver feedback.** A resolved event enters a shared receiver response queue with intended tick, quantised event tick, receiver ID, and owning transport. The queue and Cannon both call `receiverTriggerResponse`. Before the quantised attack, the receiver uses Cannon's existing pending-impact color; at the event tick it uses the same flash/squash envelope. The normal Cube renderer merges responses by receiver ID. Ripple never calls Cube DOM animation directly, and neither its planner nor response queue contains a Cube kind check. The wave stays smooth while the Cube's activation marks the quantised musical time. Visual feedback is rendered on the next available frame; audio is scheduled at the transport timestamp.

7. **Cycle boundaries.** Cycles use `[start, end)`. A receiver in the last quantisation cell belongs to tick `end − 1`, never to both cycles. Lookahead is capped at cycle end; the next snapshot begins when the transport crosses that boundary. Tests verify exact edge-distance arrivals at ticks 383 and 767, with one attack in each cycle. A stalled scheduler skips expired cycles rather than replaying them. Rendering may briefly miss a boundary during a blocked frame, but does not launch audio or fabricate elapsed cycles.

8. **Live edits.** The current cycle keeps its duration; the latest selected period starts at its next boundary. Instrument and volume remain emitter-owned. Instrument is resolved when the short (150 ms) audio lookahead commits an event, so subsequent uncommitted events use the new instrument. Shared volume/mute acts on the emitter's bus. Pause, seek, and tempo changes cancel pending sources and invalidate their generations; future events are rebuilt with the current transport mapping. Global transport is never restarted by a Ripple edit.

9. **Connections and persistence.** Ripple exposes a transport input in the existing connection graph, with no sequence output or private playback instance. Creation connects to the selected Heartbeat. Disconnecting cancels future sources, clears responses/cycles, and hides the wave. Reconnecting joins the current shared phase and schedules only remaining arrivals, without a catch-up burst. Shared Advanced connection controls expose its wire. Saved state preserves ID, position, instrument, volume/mute, and `periodLoops`; normal graph persistence preserves its connection or deliberate disconnection. Old manual records lacking `periodLoops` default to one loop and gain a default Main Heartbeat connection. Runtime rings, snapshots, event Sets, and hit progress are never saved. Deleting an emitter removes its graph port/wire and cancels its events while leaving receivers intact.

10. **Browser and audio observations.** Three radial Cubes produced C4/E4/G4 once each per one-loop cycle at offsets 96/192/240. At four loops, attacks repeated exactly 1,536 ticks apart (eight seconds at 120 BPM); lowering to 60 BPM preserved tick positions and slowed real-time expansion. Pause retained tick 2,344 and radius 75 across separate observations. Disconnect left Heartbeat advancing without additional Ripple notes or rings. Reload retained period 4 and deliberate disconnection, with no transient wave or attack. Reconnect plus Return to Start displayed radius zero. Moving the first Cube during a four-loop wave retained its first attack at tick 288; the next cycle used its new distance and attacked at 2,688. Matching Cube flashes were observed at or just after quantised ticks, depending on frame cadence. Cannon playback, isolated with Ripple disconnected, still flashed its impacted Cube repeatedly and produced nonzero audio output. No console errors were observed. Production master-bus peak was 0.126357 during the one-loop run and 0.087808 during the four-loop run. These are measured output observations, not subjective hardware listening claims.

**Checks:** 184 tests passed: 112 across the focused Ripple/Drum/palette/BoardObject/Cannon/Draw/transport/UI set, plus 72 connection, multiple-Heartbeat, main Rippler transport, and shared phase regressions. The 15 new loop tests cover periods 1–4, repeated cycles, canonical radius, pause/resume, tempo, reset, snapshot refresh, live period changes, quantisation, final slots, generic and duplicate receivers, source ownership, response timing, graph connections, reconnects, migration, persistence, and isolated deletion. Syntax checks and `git diff --check` passed.

The previous `createSimpleRippleController` manual helper remains available for compatibility tests; production Simple Ripple now uses `createLoopingRippleController`. It has no role in automatic playback. The optional `tests/simple-ripple-loop-browser.html` harness adds visible transport, note, Cube flash, ring, and audio observations for repeatable local QA.
