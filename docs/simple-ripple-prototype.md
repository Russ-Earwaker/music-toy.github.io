# Simple Ripple capability prototype

Historical first-pass report. Current looping, quantised timing and shared Cube feedback are documented in [Simple Ripple transport timing](simple-ripple-timing.md).

This version plays **only on manual emission**. It neither captures a loop nor creates hidden DrawGrids. Cannon keeps its existing capture/DrawGrid/transport behavior.

1. **BoardObject schema.** `kind: ripple`, stable `ripple-...` ID (UUID when available, with a unique fallback for local-network HTTP), logical position/rotation, compact radius bounds, and `draggable`, `triggerEmitter`, `instrumentSource.instrumentId` capabilities. Authored state contains instrument, volume/mute and fixed defaults (speed 360 logical units/second, range 720). `owns` and both reference lists are empty. The emitter queries shared receivers; it never owns Cubes.
2. **Creation/retrigger.** Simple Music → Ripple → click empty board space creates the emitter and emits once. Clicking its ◎ body emits again. The separate circular handle reveals controls or drags. Instrument selection uses the existing instrument picker, and volume/mute uses the shared volume UI. The action body and handle have separate hit areas. Advanced uses the same object; there are no new musical internals to reveal.
3. **Runtime waves.** Each emission has a unique runtime wave ID, latched emitter state/origin, start audio time, speed/range and a Set of receiver IDs. SVG circles are presentation only. Radius is elapsed AudioContext time × logical speed. Waves expire at maximum range and disappear on deletion/load; none are saved.
4. **Receiver detection.** `board-wave.js` accepts any BoardObject with `triggerReceiver`. It computes nearest logical rectangle/circle-bound distance, including rotation, then checks `previousRadius < distance && currentRadius >= distance`. A Set prevents repeated hits, including duplicate receiver entries. Origin overlaps are included. Objects beyond range are skipped. No Cube kind check is involved; a test uses a different painted-shape kind with the same capabilities.
5. **Shared resolver.** Ripple's wave planner and Cannon's `bouncerGridState` both call `resolveBoardInteraction`. Receiver `pitchSource` supplies MIDI, emitter `instrumentSource` supplies instrument, and contact supplies time. Missing musical data stays silent. Cube gains no instrument property.
6. **Musical timing.** At emission, the wave performs an analytical sweep over its full range, sorts arrivals and maps arrival seconds into Main's current 96-PPQ tick domain. Fractional ticks preserve exact arrival rather than snapping a note away from its visual contact. The existing `triggerInstrument` path schedules future Web Audio sources using those arrival timestamps. Animation never triggers notes, and there is no Ripple-specific polling scheduler. Manual emission also works while Main is stopped. Sample pitch shifting is explicitly enabled so the receiver's octave is preserved.
7. **Shared Cube proof.** Tests exercise actual Cannon simulation → canonical DrawGrid conversion and Ripple's wave → the same receiver, with G4/67 preserved under Cannon Kalimba and Ripple Piano. Browser observations confirmed the same C4 Cube under Piano and Kalimba Ripples and Cannon Kalimba; the Cannon used its ordinary captured DrawGrid playback.
8. **Decorative Art.** Flash Circle was placed among the receivers. It has no `triggerReceiver`; only the three Cube notes were emitted. There is no Art exclusion list and no musical capability added to Art.
9. **Persistence/deletion.** Scene snapshots add an optional `rippleObjects` array of version-1 BoardObjects. Old scenes without that array load an empty list. Restore validates before replacing records, preserves IDs/position/instrument/volume/mute, regenerates capabilities, and discards unknown/transient data. The shared board creation/move/remove API includes Ripple. Handle dragging uses ToySpawner's normal large-trash flow with the emitter's removal callback; deletion cancels pending emitter audio/waves and leaves all receivers untouched. New scenes clear emitters and runtime state.
10. **Architecture audit and limits.** No `if ripple` or `if cube` branch was added to the generic musical resolver or wave interaction layer. Kind registration, palette selection, persistence and Ripple rendering/input necessarily identify the new kind. Existing Cannon-specific collision geometry/capture code remains unchanged. This prototype latches receiver geometry/pitch, emitter instrument and tempo at emission: moving an emitter affects its next wave; moving/editing/deleting a receiver during an already scheduled wave does not revise that wave's events. Waves are manual performances independent of Main's Play/Pause; loading/deleting resets them. These choices keep the prototype on the existing audio path without introducing a live rescheduling system.
11. **Browser/audio observations.** Tested on a fresh local origin using the actual app and the optional QA observer. Piano emitted C4, E4, G4 in increasing radial arrival order, one event each. A Kalimba Ripple produced those same pitches; another Piano emitter triggered the same receivers independently. Production master-bus peak values were nonzero (Piano 0.092696, Kalimba up to 0.128287). Isolated Cannon C4/Kalimba playback measured 0.100739. These are actual output-bus measurements plus production note events, not a human listening/timbre assessment. Emission after moving used the new geometry; deleting a moved Ripple through shared trash preserved all three Cubes, Art and Cannon. Saved emitters reloaded with stable IDs and without re-emitting. Shared volume changed authored state from 1 to 0.99. No console errors were observed.

The previous live Paint verification debt was also exercised: draw/play, reveal controls with the normal keyboard interaction, Straighten → Re-coil state, then handle-drag to the shared trash. Paint disappeared while the three Cubes and Cannon remained. Ripple controls were verified with mouse input. Existing Paint pointer-control behavior was not refactored.
