# Trigger starters and initial Ball trajectory

1. **Shared seeding helper.** `trigger-starter-cubes.js` supplies `seedTriggerCubes` to Ball arming and Ripple arming. It calls the canonical physical store's `addCube`, which is also the target of shared BoardObject/manual Cube creation. Selecting either Trigger can seed Cubes; selecting Cube itself does not. Ball's main palette dispatch now enables this behavior instead of bypassing it with `seed: false`. Toggling a tool off does not seed anything.

2. **Nearby rule.** At selection, the likely creation point is 47% across and 52% down the board viewport, converted through `screenToWorld`. A canonical Cube with `triggerReceiver` and a valid `pitchSource` whose center is within **650 logical board units**, inclusive, prevents all seeding. No CSS-distance test is used. One suitable existing Cube is enough; the helper does not top up to three. Pan and zoom affect the conversion of the likely creation point, not the logical radius.

3. **Placement and ownership.** When no suitable Cube exists, create three at offsets `(-110, -50)`, `(110, 15)`, and `(0, 170)` relative to that point. This retains the earlier Bouncer starter pattern and existing optional tumble-in animation. Authored positions are final immediately. The Cubes use normal generated IDs, pitch assignment, dragging, hit response, and persistence. There is no starter class, owner ID, or private Trigger copy. Canceling creation or deleting a Trigger leaves them on the board, available to other Triggers.

4. **Initial Ball trajectory.** After a valid drag exceeds the existing six-unit creation threshold, a transient SVG polyline displays the full projected flight, including bounce corners. It is updated immediately on pointer movement and when Cube geometry changes; a cached geometry/tempo/duration key avoids repeating simulation for unchanged frames. The temporary origin/direction stays in the input gesture, with no Ball or Cannon created before release. The direction arrow is a fixed 96 units, matching the Cannon barrel, so drag distance does not imply increased power. Both preview and release use the same `launchFor` function and `boardLaunch` normalization at fixed speed **840**.

5. **Shared Cannon calculation and rendering.** Initial creation and authored Cannon aiming call `predictCannonTrajectory`, which returns the real `simulateThrow` swept-collision trajectory. The committed throw calls that same simulator to capture music/flight. No approximate preview algorithm was added. Both preview polylines use the existing `physical-path-prediction` style and the same point-rendering function. Existing Cannon prediction also refreshes its cache on current tempo or phrase-length changes. Existing aiming/rethrow semantics remain intact.

6. **Release and cancellation.** Release resolves the same launch origin/vector and commits the normal Cannon/Ball capture, then the authored path takes over. The transient polyline and direction arrow clear. Escape, pointer cancellation, lost capture, blur, selecting another creation tool, load, and disposal also clear preview state. Canceling before release creates neither a Cannon nor a Ball. Tests compare all preview coordinates against a real simulation using the released launch, including moved Cube geometry, and verify that longer drags do not change speed. Existing swept-collision tests remain passing.

7. **Regression tests.** **151 tests passed** across Trigger starters, actual board input, Cannon, automatic Ripple, palette, BoardObject, Drum, Draw, UI mode, transport, and containers. New checks cover canonical/persisted starter objects, the inclusive logical radius, either Trigger order, actual Ripple arming, actual Ball palette dispatch, starter preservation on Cannon deletion, initial direction updates, current Cube geometry, exact preview/release equivalence, fixed velocity, cancellation/lost capture/blur, and authored preview tempo/length. The Ripple suite includes periods 1–4, quantisation, feedback, snapshots, live dragging, newly placed Cubes, duplicate-note suppression, pause/resume, tempo, Return to Start, and reconnects. Seeding adds ordinary receivers without changing those timing rules.

8. **Browser observations.** Two isolated fresh scenes exercised Ball-first and Ripple-first selection. Ball seeded exactly three C4/D4/E4 Cubes before any Cannon or Ball existed. A changing-direction drag produced four distinct trajectory samples; its final horizontal preview matched every coordinate of the committed trajectory, with velocity `(840, 0)` and a collision at tick 48. Audio and Cube response were observed. Selecting Ripple on that board kept the same three Cube IDs, and Ripple played their pitches under normal Heartbeat playback. In the reverse order, Ripple selection seeded three Cubes before placement; after placement and Play, it looped over them, and selecting Ball reused them. Production audio output was measured rather than assessed through subjective hardware listening. No console errors were observed in the checked scenes.

The optional `tests/trigger-starter-browser.html` harness exposes Cube IDs, transient path samples, exact committed-path comparison, note observations, and master-bus peak for repeatable manual QA.
