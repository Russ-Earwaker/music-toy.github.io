# Simple Drum prototype

1. **BoardObject schema.** Drum is a version 1 BoardObject with `kind: drum`, stable ID, position, circular bounds (radius 52), and `appearance.variant: pad`. Its only capabilities are `draggable`, `playable`, and `instrumentSource`. Authored sound state contains instrument, volume, mute, and an internal fixed MIDI pitch of 60. It has no trigger or loop capability.

2. **Playable dispatch.** The performance surface calls `createBoardPlayableController.activate(id)`. `resolvePlayableActivation` checks `playable` plus `instrumentSource`, then resolves source ID, instrument, MIDI pitch, volume, mute, and current audio time. The injected performer uses the existing audio engine. The resolver and controller contain no Drum kind checks. Decorative objects without these capabilities do not resolve musical events.

3. **Tap versus drag.** The reusable pointer helper uses a 6 CSS pixel threshold. A completed tap performs; crossing the threshold moves the object and suppresses the release hit. Canceled gestures do not perform. Pointer-generated clicks are suppressed to avoid duplicate attacks; keyboard activation remains supported. A separate handle opens the hidden controls or drags the object. Placement stays armed for repeated empty-board taps, while selecting Drum alone creates nothing.

4. **Sound and instrument.** Each Drum defaults to the existing `DRUM KICK` voice. It uses the shared instrument chooser and volume/mute implementation, including non-percussion choices. Changes affect subsequent taps immediately. C4 is an internal fallback for sample sources that need pitch; no pitch control is exposed. Each tap requests a fresh attack, without quantization or performance debounce. The 140 ms squash/brightness feedback is presentation-only.

5. **Transport independence.** Activation reads audio-context time and calls the existing instrument engine directly. It does not inspect, start, stop, reset, or quantize against Heartbeat. There is no recording, capture, sequencing, or loop state.

6. **Persistence and deletion.** Scene snapshots add an optional `drumObjects` array; older scenes restore an empty array. Restore validates authored records and reconstructs capabilities, stripping runtime/unknown state. Position, instrument, volume, mute, stable IDs, and the pad variant survive reload. Shared trash removes the object, cancels its scheduled sources, invalidates pending audio, disconnects its bus, and removes its own volume/mute settings. Other objects' buses remain intact. Removing a Drum also closes its picker and cancels its gestures and animation.

7. **Multiple Drums.** Browser QA placed three independent Drums, assigned Kick, Snare, and Piano, and set Snare volume to 0.5. Mouse and rapid simulated touch taps produced the respective instruments. Moving the first changed only its position; deleting it through shared trash preserved the other two and their settings. Both remaining Drums restored with their IDs/settings and played immediately after audio unlock.

8. **Drum-specific musical code.** No `kind === 'drum'` branch was needed in generic musical dispatch. Drum-specific code defines its default instrument, fixed pitch, model adapter, UI, and the main application wiring of its store into the generic performer. Kind checks remain in schema restoration and object creation/adaptation, rather than event resolution. This prototype supplies the Drum store to the controller; future playable stores can use the same controller/resolver.

9. **Browser and audio observations.** The isolated browser harness verified repeated placement, controls, independent instruments/volume, mouse taps, simulated touch pointers, drag without a hit, transport stopped/running, shared trash, and reload. Three mouse taps plus nine touch taps produced exactly twelve note events. Dragging preserved that count. Three more taps while transport ran produced three more notes without restarting transport. Production audio-bus measurement showed nonzero output (peak 0.436281 during the mixed-instrument run). Reloaded Snare/Piano produced two correct events and nonzero output while transport was stopped. No console errors were observed. Touch was synthetic pointer simulation, not a physical device; audio was measured, without a subjective hardware listening assessment.

**Validation:** 97 tests passed across Drum, palette, BoardObject, Ripple, Bouncer, Simple Draw, board interactions, UI mode, and audio transport. Focused coverage includes capability-based resolution, mouse/touch duplicate suppression, repeated attacks, transport independence, independent settings, persistence, placement, and isolated audio-bus cleanup. The optional `tests/simple-drum-browser.html` harness adds visible note/audio observations to the real application for repeatable manual QA.
