# Drum loops, Drum Set and Trigger receivers

This supersedes the live-only behavior in `simple-drum-prototype.md`. PLAY offers Drum (repeated individual placement) and Drum Set (an immediate convenience action). Tapping a Drum records a quantised hit, with no Record mode.

1. **Set composition and layout.** The action creates six ordinary Drum BoardObjects, not a DrumSet object or group scheduler. Relative to the converted board viewport creation point: Kick `(45,170)`, Snare `(-70,0)`, Hat `(-285,-10)`, High Tom `(-100,-170)`, Low Tom `(100,-170)`, Cymbal `(285,-10)`. All pad centers are over 150 logical units apart, with 104-unit pads and separate handles. Each object has its own sound, volume (initially 0.8), one-loop period, empty pattern, normal ID, movement and deletion.

2. **Existing instrument mappings.** These IDs are present in `samples.csv`; no synthesis engine or sample asset was added.

| Kit role | Instrument ID | Mapping |
| --- | --- | --- |
| Kick | `DRUM KICK` | Existing kick |
| Snare | `DRUM SNARE 1` | Existing snare |
| Closed Hat | `HI-HAT CLOSED` | Existing closed hat |
| High Tom | `DRUM SNARE 2` | Higher percussion substitute; library has no named tom |
| Low Tom | `DRUM BASS` | Bass-drum substitute for the lower tom |
| Cymbal / Crash | `HI-HAT OPEN` | Open-hat substitute; library has no named crash |

Every member retains the shared instrument chooser, including non-percussion choices. C4 remains an internal stable sample pitch without a pitch editor.

3. **Live-hit semantics.** The generic playable controller still resolves capabilities; its production performer delegates to the Drum loop controller. A hit starts/resumes its connected Heartbeat if necessary, retaining its position. It selects the next 48-tick slot using the factored canonical Rippler forward-grid helper at 96 PPQ. The established strict-next-slot rule also advances a hit exactly on a slot boundary. At 120 BPM the maximum quantisation wait is 250 ms. There is no extra immediate preview attack. The canonical marker fills at admission; audio and the common pad pulse are due at the quantised tick. Trigger times already on the grid are kept rather than advanced another step. A final Ripple slot at tick 383 resolves to the Drum downbeat at 384, without double quantisation.

4. **Canonical music representation.** `authoredState.pattern` is normalized, ordinary DrawGrid authored state: version 3, `steps`, `authoredDurationTicks`, `instrument`, `authoredNotes` with stable IDs, `col` and `sourceMidi`, and the normal node projection. There are 8 slots per toy loop. One note per column is canonical. UI cells do not own or schedule music. This uses normal musical data directly; it does not create a hidden panel, a second graph type, or a new Advanced editor/container concept.

5. **Timeline and clearing.** Revealed controls contain Instrument, shared Volume/Mute, Period and a horizontal slot strip. Thick divisions mark each eight-step loop, with horizontal scrolling for longer patterns. Filled markers are buttons that remove that canonical hit, satisfying pattern clearing without another large Clear action. A short hint explains this interaction. The current slot is read from Heartbeat on presentation frames. Tapped, triggered and replayed strikes all use the same controller feedback subscription and pad squash/brightness animation. Controls flip above a pad when necessary to stay within the viewport.

6. **Period and phase.** Periods 1–4 correspond to 384–1,536 ticks and 8–32 slots. Play/seek admit a stored boundary note synchronously, so the first periodic poll cannot miss it. The controller is serviced by the existing application audio scheduler and enumerates events with `ripplerEventsInWindow` and phase origin zero. It owns no timer. Pause freezes musical phase; BPM remaps time without changing slots. Return to Start retains patterns and includes a stored downbeat when resumed; ordinary pause/resume does not replay a note already heard on its boundary. Period edits apply immediately against the same Heartbeat phase; shrinking removes hits outside the shorter timeline. Future events are invalidated/rebuilt without restarting transport. Instrument/volume edits cannot retrigger an already-sounded boundary note.

7. **TriggerReceiver integration.** Drum now has `draggable`, `playable`, `instrumentSource`, `triggerReceiver` and `loopSource`, but no `triggerEmitter` or `pitchSource`. Ripple queries the shared BoardObject list and preserves one receiver activation per cycle. Cannon and its initial preview share a capability-based collision-body adapter, including Drum circles. Its swept simulation tests circles and existing Cube boxes together, with exact circle reflection and high-speed contact detection. Receiver-owned Cannon hits are admitted only after physical contact, preventing an untravelled predicted collision from recording prematurely.

8. **Receiver-owned sound policy.** `triggerReceiver.soundSource: 'receiver'` selects the receiver's playable/instrument capabilities in `resolveBoardInteraction`. Cube's default continues to use emitter instrument plus receiver pitch. There is **no Drum kind check** in that resolver, the Ripple event path, or collision adaptation. Another kind declaring the same capabilities works in tests. Receiver-policy events route into the same Drum pattern admission used by direct play. Cannon's internal DrawGrid excludes these events, so a Snare collision does not also produce Kalimba. The old `cubeId` collision/reference field continues carrying receiver IDs for compatibility; it confers no ownership.

9. **Ripple results.** A Piano Ripple traversed all six kit members. Each recorded its own appropriate instrument, and no Drum used Piano. The two-loop Kick accumulated slots 6 and 14 across successive one-loop waves; the other members retained one-loop patterns. The Cymbal's end-of-wave arrival recorded slot 0 correctly. Existing live-drag, newly placed Cube, geometry snapshot and quantisation behavior remain covered. Existing receiver-owned pads also count as usable starter targets, so selecting Ball/Ripple over a kit does not scatter starter Cubes onto its pads.

10. **Ball results and duplicate control.** A default Kalimba Cannon struck the cleared Hat pad with a swept circle collision at quantised tick 48. The Hat recorded slot 1, played `HI-HAT CLOSED`, and replayed it on later loops; no Kalimba event was generated for that collision. Per-Drum admission keys prevent live taps, trigger hits and loop lookahead from duplicating the same absolute tick. Identical simultaneous instrument/pitch events across Drums share one audible voice, while every Drum records and animates. Different sounds and ticks remain independent. The first audible source owns that shared voice; deleting or editing it can transfer a still-future attack to another admitted source. Already-sounded attacks are never transferred/replayed.

11. **Persistence and deletion.** The existing optional `drumObjects` scene field stores normalized authored pattern, period, instrument, volume/mute, label, ID and position. Old records default to empty one-loop patterns and gain a default Main connection through the existing root migration; deliberately disconnected new records stay disconnected. Normal graph persistence records each Heartbeat input. Runtime admission sets, cursors, pending seek flags, feedback and animation state are excluded. Shared trash removes only that Drum, its pattern and audio bus/settings; the remaining set is independent. Browser deletion removed Low Tom and reload restored the other five with the same properties and patterns, silent until playback resumed.

12. **Browser and audio observations.** A fresh PLAY → Drum Set produced six separated pads. Kick/Snare/Hat taps landed at ticks 48/96/144 and repeated 384 ticks apart with no duplicate note entries. The two-loop Kick control displayed sixteen slots; tapping a filled cell removed only that hit. Pause stopped phase advancement. Ripple and Cannon checks produced receiver-owned instruments, recorded markers and pad feedback through the same path. Reloaded patterns played again from Heartbeat phase zero without an automatic stale attack. No console errors were observed. Measured production master-bus peaks included 0.161809 for live capture/replay, 0.275005 for the triggered kit, and 0.160183 after reload. Audio was measured and instrument/tick identities inspected; subjective hardware listening was not performed. Visual feedback appears on the next available frame, while sound is scheduled by transport time.

Focused additions cover kit separation/mappings, canonical 1–4-loop patterns, forward admission and boundary wrap, duplicate suppression, receiver-owned resolution using a future kind, real Cannon capture/routing, swept high-speed circles, timeline projection/removal/playhead, pause/resume/BPM/reset, connection invalidation, persistence, isolated deletion and shared-voice cancellation. Syntax and whitespace checks passed.
