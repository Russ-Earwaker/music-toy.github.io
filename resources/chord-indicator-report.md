# Active chord feedback

1. **Authority:** the board's existing visual frame reads the selected playback occurrence via `getPlaybackInstance(toy.id)` and its owning Heartbeat's current tick. `resolveChordAtTick(instance.context, currentTick)` supplies the label, using the same resolver and inherited harmony context as audio pitch processing. Lookahead scheduling cannot advance the badge. There is no independent clock, counter, or persisted chord display state.
2. **Affected toys:** harmony-aware pitched Melody/Accompaniment playback on DrawGrid, Bouncer and Rippler, including their Instances. Role classification shares the audio boundary's instrument catalog and compatibility logic. Simple Rhythm, Drum Kit, percussion instruments and explicit Percussion roles show nothing. Chord Wheel retains its independently authored voicing policy and shows no misleading adaptation badge. Inactive, future, disconnected and context-free playback hides its badge. Musical role remains Advanced-only.
3. **Simultaneous occurrences:** the badge follows the existing single visible playhead: newest currently active turn, with the existing occurrence-ID tie-break. Other audio occurrences continue independently. No state is shared through the Master; separate Instances can show different chords simultaneously. A regression covers conflicting C/F occurrences of one source.
4. **Pause and transport:** pause hides badges, matching the board's active-playback highlighting convention. Resume re-resolves at the retained tick. BPM changes affect audio-time conversion, not chord position. Seek, Return to Start and complete arrangement loops resolve from the current occurrence and current tick.
5. **Visual treatment:** a compact bordered chord label in the header, positioned absolutely beside the toy name so it adds no layout width or height. Masters use the existing gap to the left of the name to avoid overlapping buttons; Instances show it to the right. Chord changes receive a brief 300 ms background emphasis, disabled for reduced-motion preference. Overview visibility is retained. Text/style updates happen only on changes; pause hiding does not repeatedly write DOM attributes. No source-note overlays or new explanation text were added. The requested future note-visualisation item is in [harmony-feedback-backlog.md](harmony-feedback-backlog.md).
6. **Verification:** 919 tests passed, including seven new regressions for event boundaries, inactivity/context absence/percussion, independent Master/Instance context, real transport pause/BPM/seek/Return to Start, DOM updates, conflicting occurrences, and two complete 16-bar arrangement cycles. The five indicator tests passed again after the final DOM-write guard. Browser exports verified **362 visible transitions** against event-time harmony and **10 pause hides**, including normal UI tempo/resume, direct Masters, unrelated pitched playback and unchanged 240 × 160 Instance dimensions. Intro/A/Outro displayed C → Am → F → G; both pitched B Instances displayed F → G → Am → C. Rhythm Instances and idle Masters remained clear.

The badge renders at the existing playhead frame cadence. Browser background throttling can delay visual frames; it does not create a separate harmony phase or advance the badge to scheduled future notes. Browser checks establish display/scheduling consistency, rather than a subjective listening judgment.
